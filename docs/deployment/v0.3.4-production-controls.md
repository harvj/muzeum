## Operator-only production snapshot procedure if existing evidence fails

1. Authorize a named backup operator with existing read-only Restic repository and escrow access, the exact snapshot ID, and a disposable Ubuntu 24.04 x86_64 VM with encrypted scratch storage. The current Muzeum SSH account has no standalone recovery grant. Do not add sudo grants or use the production deployment coordinator to trigger recovery. Block routes to the production host and live databases. Use a root-only 0700 working directory and 0077 umask. Allow outbound repository access only for retrieval.
2. Read the protected backup receipt and run `restic restore "$snapshot_id" --target "$restore_root" --verify` with the existing protected credential files. Compare the capture-manifest checksum with the backup receipt. Verify every payload hash and record elapsed time. Keep production configuration and key material root-only and disable external access after retrieval.
3. Initialize a fresh PostgreSQL 16 cluster on a private socket or isolated loopback inside the VM. Create four unique `muzeum_recovery_` database names for each artifact. Use fresh credentials and separate local owner and application roles. Restore each dump with `pg_restore --no-owner --no-acl --exit-on-error --dbname=<isolated-target>`. Compare every database fingerprint against the snapshot metadata with the existing fingerprint implementation before starting any app. Use separate working copies for both artifacts.
4. Stage both exact app SHAs and frozen bundles against the reviewed Ruby 3.4.13 tree. Construct isolated application config with all four URLs explicitly remapped. Use the minimum protected keys only where needed for local decryption checks. Disable provider credentials and outbound traffic, and confirm the production DB addresses and Auth endpoints are unreachable. Verify schemas, observation and evidence fingerprints, local decryption, and Puma HTTP 200. Run Solid Queue with recurring scheduling disabled and a queue config restricted to a new recovery probe queue. This prevents restored pending jobs from executing. Enqueue the shipped OpsProbeJob on that queue and verify its write to isolated Solid Cache.
5. Record hashes for the actual Commons SVGs used in the Linux rehearsal, regenerate both PNGs using the staged libvips, and verify dimensions, warm lookup of an isolated checksum-keyed output and missing-asset text fallback. Muzeum itself renders the remote image URL. This staged output cache has no effect on production and is separate from browser cache behavior.
6. Keep a redacted receipt with snapshot and artifact IDs, manifest and runtime checksums, four fingerprint results, restore and per-app timing, HTTP and queue results, and image evidence. Stop isolated processes, drop the exact disposable targets, revoke temporary restore access, and destroy the VM's encrypted working volume and key. Retain only the protected redacted receipt.

Verify the manifest is readable by root and by the muzeum service, is root:root 0644, and is not writable by muzeum. Check that each parent directory is root-owned, traversable, protected from group and other writes, and is not a symlink. Run the runtime selector for both approved artifacts as root and as muzeum before reloading systemd definitions. Capture previous destination files, owners, modes and checksums. With separate installation authorization, hold both existing phase and backup locks and confirm there is no active deployment. Stage root-owned temporary files on each destination filesystem, verify, and rename into place. Reload systemd definitions only. Do not restart any unit. On installation failure restore the previous files and definitions. The old shared Auth runtime remains untouched.

Use the separate guarded release checkout and the clean deployment-control checkout. The control checkout still needs review, its own CI, and an explicit v0.3.4 scope entry. The exact v0.3.4 forward SHA uses its successful main push CI with all required jobs checked. Other release branches retain their branch-push requirement. The v0.3.4 control checkout tracks controls/v0.3.4 and independently requires successful exact-SHA push CI. Preflight must verify the helper handshake, patched runtime manifest, locked bundles, live baseline, fresh encrypted backup, isolated recovery receipt and health. The selector allows only the three named SHAs in this draft. Future application SHAs require a reviewed profile. The fallback remains a separately authorized manual recovery under both locks. Verify schema compatibility and the failed forward receipt before selecting the prepared rollback release on Ruby 3.4.13. No ordinary ancestry bypass or automatic rollback is included.
