# v0.6.0 rollback compatibility

The rollback build starts at production v0.5.1 and understands the new edition-slot columns when present. The release page, tracklist evidence, and catalog refresh read and write base slots separately from additional appearances. Release membership and distinct-observation aggregation still use all verified slots. Additional appearances and the independent recording and first-release dates remain readable. Musical Identity decisions remain in the database while their v0.6.0 editing and color presentation are unavailable in the v0.5.1 interface.

Retain production v0.5.1 at `4d9ff5728e8375d795ebc141bcfa9d57cbefca1d` as the historical artifact. Use this compatible checkout as the application rollback for candidate `1c1d75fee397e06622a41f01a224faec1c54c9cd`. Use the existing minimal Capistrano application rollback procedure. Leave the database at the v0.6.0 schema. Never run the edition-slot migration down over live memberships.

## Disposable database rehearsal

Use one fresh PostgreSQL database named `muzeum_edition_rollback_test` and export its `DATABASE_URL` with `RAILS_ENV=test`. Use Ruby 3.4.13 and the frozen bundles.

1. From the exact v0.6.0 checkout run `bundle exec rails db:prepare`.
2. In that checkout run `bundle exec rails runner /path/to/rollback/ops/catalog/seed_edition_slot_rollback.rb > /tmp/muzeum-rollback-fixture-ids`.
3. Switch to the rollback checkout. Run `bundle exec rails runner ops/catalog/check_edition_slot_rollback.rb /tmp/muzeum-rollback-fixture-ids`. Keep the same database and skip database preparation in this checkout. The script signs in using a disposable local session, checks rendered release and recording pages, and compares catalog, chronology, evidence, source, and decision data before and after the requests.
4. Separately run the regular v0.5.1 Rails and Chrome tests against a different disposable database initialized by the rollback checkout.
