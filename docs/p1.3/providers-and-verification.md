# P1.3a provider contracts and verification

## MusicBrainz

Use public HTTPS GET requests to `/ws/2/recording` for candidate discovery and `/ws/2/recording/{mbid}` for identity verification. Fetch release details including recordings and media when verifying a track slot. Model the recording MBID, artist MBIDs, ordered artist credits with credited names and join phrases, recording length and disambiguation, and typed release, release-group and track IDs. Preserve partial dates and country as reported. Search fields and lookup includes are endpoint-specific. Distinguish edition track ID from its nested recording ID. Preserve result count and offset so a page cap or truncated relationships cannot appear exhaustive. Public reads need no login credentials. Confirm the application's use classification before relying on the public service. [API](https://musicbrainz.org/doc/MusicBrainz_API), [search fields](https://musicbrainz.org/doc/MusicBrainz_API/Search), [data licensing](https://musicbrainz.org/doc/MusicBrainz_Database/License).

Use an identifying User-Agent with version and operator contact and a shared limit of at most one request per second across Muzeum workers on the egress IP. Respect 503 throttling, 429 and valid Retry-After. Treat bounded timeouts, transient 5xx and malformed or incomplete success payloads as unavailable evidence. A confirmed 404 on an MBID lookup records a failed claim and is distinct from an unavailable lookup. Record requested and returned identifiers when a redirect can be verified. [Rate limiting](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting).

Cache validated public responses by provider, endpoint, normalized request parameters and parser version. Coalesce concurrent misses where practical. Use a shorter lifetime for verified negative lookups. Store evidence used for a decision independently from the disposable request cache, with fetch time and normalized fields or digest sufficient for review. Exclude credentials and listener identity from provider queries and logs. Persist cooldown and retry due times in work state. Defer attempts with bounded jittered backoff and allow explicit replay of exhausted work. An outage leaves current decisions intact and never interrupts Last.fm capture.

## Discogs

Discogs is supplementary and currently inactive. Proposed catalog reads use release details by release ID, master/versions where useful, and authenticated database search only if needed. A known public release can be read without listener account access. Database search requires operator-approved application credentials or a server-side personal access token for an operator-run pilot. Keep any approved token in the existing secret mechanism. Use the official API and a descriptive User-Agent. Do not use marketplace, collection/wantlist or image data. [Developer reference](https://www.discogs.com/developers/).

The commonly documented limits are 25 unauthenticated and 60 authenticated requests per minute. Treat these as provisional, because the developer reference returned HTTP 403 during this review. Confirm limits and endpoint authentication before activation. Observe the returned rate-limit, used and remaining headers, share a budget below the applicable limit, and honor 429/Retry-After with an independent cooldown. Neither a failed lookup nor absent credentials blocks MusicBrainz resolution.

Capture catalog release ID, master ID where supplied, country, release date or year, ordering and track position if useful. The track reference is the edition and slot, including subtrack path when present. It is not a MusicBrainz recording identifier. A supported correspondence requires separately recorded evidence. An observed album can help narrow investigation without determining identity or per-play release credit.

The terms distinguish CC0 catalog fields from restricted data, require retaining API content only as needed, and prohibit presenting content more than six hours older than the version on Discogs. Before activation, approve the minimal retention required for auditable decisions, enforce cache expiry and refresh before display, and omit stale content when refresh fails. Add the required API non-affiliation notice and linked “Data provided by Discogs” attribution next to displayed data, with link behavior conforming to the terms. Keep raw responses out of permanent decision history pending review. [Discogs API Terms of Use](https://support.discogs.com/hc/en-us/articles/360009334593-API-Terms-of-Use).

## Tests for the first writable slice

Run at the HTTP consumer, persistence and authorized query boundaries against PostgreSQL. Start with the repository's MusicBrainz search and release JSON fixtures, then add sanitized, deterministic lookup and search envelopes that follow the published contract. Preserve nested artist credit, `media[].tracks[].recording.id`, counts, offsets and error headers. Add Discogs contract fixtures only when its adapter is approved. Disallow live provider traffic in CI.

| Case | Required assertion |
| --- | --- |
| Idempotency and concurrency | Two selection runs attach an observation once per compatibility version. Two workers competing for one group cannot duplicate assessments or decisions. A repeated completed evaluation leaves the same effective result. |
| Contradictory or absent source MBID | An unrelated, missing, redirected or malformed claim never silently becomes identity. Search still yields candidates where possible. Assert claim and contradiction provenance. |
| Similar names and ambiguity | Studio, live, remix and alternate candidates sharing title or artist remain separate. A tie, truncated page or disputed slot preserves alternatives and yields no automatic decision. |
| Supported case | A verified claim, agreeing artist/title and an independently corroborating edition slot produces one recording, one attributable decision, and one scoped effective result once acceptance is approved. Two supported editions of the same recording do not create a second recording. |
| Outage and throttling | Simulate timeout, 429 with Retry-After, 503 and malformed success. Assert retry/cooldown persistence, preserved decisions and successful independent Last.fm import. Simulate successful retry with a deterministic clock. |
| Source preservation | Compare scrobble IDs, timestamps, payloads, fingerprints and fetch/page/delivery lineage before and after success, failure and retries. Exercise database source protection. |
| Shared archive | Give two users access to one observation. Assert one shared default and independent overrides, explicit unresolved overrides, release-credit independence, and revoked access to private reads and writes. Also deny access from a different archive with identical metadata. |
| History | Assert actor, UTC time, policy version, evidence, scope and predecessor. A no-change assessment creates no decision. A revert appends a decision. Database guards refuse mutation of previous entries. |
| Interruption recovery | Interrupt before queue handoff, after fetch, during finalization and after commit before acknowledgement. Reclaim expired leases, reject stale tokens and assert an atomic, single result. |
| Pilot limits | Stop at the fixed keyset bound and explicit caps even while source rows arrive. Repeated runs and cache hits preserve bounds and provenance. |
