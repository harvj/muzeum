# Muzeum numbered roadmap

Canonical roadmap, updated 2026-11-18. This file supersedes milestone ordering and authentication requirements in the dated repository assessment, January notes, P1.0 proposals and original P1.1 plan. Those documents remain historical evidence. Muzeum is the application; no legacy Muzeus database migration is planned.


## Product direction

**Primary daily use: "What am I pulling off my shelf next?"** Muzeum helps a listener explore, remember and choose from their own music, not merely maintain a catalog or browse raw scrobbles. Canonical identity, provenance, listening statistics and musical knowledge enable this. Near-term selection should work with existing counts, recency and relationships; future rich queries can intersect preferences with musician/instrument/event annotations. Preserve honest distinctions between Last.fm-reported scrobbles and actual playback completion.

## Canonical product specifications

The authoritative, living domain rules are [principles](domain/principles.md), [recording resolution](domain/recording-resolution.md), [release assignment](domain/release-assignment.md), and [listening statistics](domain/listening-statistics.md). They distinguish source observations, canonical recording identity, release membership, per-play credited release, automatic contextual reassessment, user overrides and disjoint release rankings. The documents specify intended behavior, **not** shipped implementation. See root [AGENTS.md](../AGENTS.md). These current policy decisions supersede conflicting historical proposals.

6. **P1.3c — Release relationships and contextual attribution.** Reconcile provider editions and track slots into Muzeum collection membership. 7. **P1.4 — Expanded canonical Artists, Releases, Recordings and Plays library (tentative).** Build compact tables, search, filters, track listings and listening histories around canonical music. Membership views show all activity of included recordings. Release rankings use at most one credited release per play. Use Muzeus once as a visual reference and reflect new committed listens without refresh. Include a practical early shelf-selection experience using known recordings, frequency, recency and collection navigation. Design a deliberate artist/release/recording metadata contract and a repeatable **Import** action to refresh selected MusicBrainz/Discogs fields with provenance, comparison and safe change history; avoid indiscriminate provider mirroring.
   - **P1.4 table and style restoration (deployed).** [Issue #22](https://github.com/harvj/muzeum/issues/22) covers dense linked desktop tables, grouped mobile rows and full-name disclosure, browser-local day groups, continuous track numbering, section cards, Profile navigation, appearance controls and the published-version footer. [Accepted screenshot evidence](design/README.md#table-fidelity-revision). Ranking and play/time badges remain in [issue #21](https://github.com/harvj/muzeum/issues/21).
   - **P1.4 Resolution performance and reliability (candidate).** [Issue #25](https://github.com/harvj/muzeum/issues/25) covers faster archive-scoped Resolution reads, distinct recording and edition actions, and bounded Discogs failure recovery with retained MusicBrainz evidence. [Investigation and verification](p1.4/resolution/README.md).
   - **P1.4 Site Art integration (candidate).** Browser-decoded backgrounds and favicon from the Site Art manifest, with bundled fallbacks and asynchronous refresh. [Issue #27](https://github.com/harvj/muzeum/issues/27).
   - **Open — Genre buckets.** Muzeus used explicitly edited category values, with category inheritance at artist/release import and edit points. Its palette was black, brown, salmon, pink, orange, yellow, green, forest, blue, purple, grey and ground. Muzeum has no equivalent classification field or reviewed source. Decide how listeners will establish and maintain those buckets before showing the historical colors on catalog rows.
8. **P1.5 — Richer reporting and refinements (tentative).** Add rebuildable, scoped aggregates, charts, durations and rankings as the interpretation contracts stabilize. Generic external recommendations, Spotify, playlists, streaming and social features remain deferred; **choosing and rediscovering from one's own shelf is not deferred**.

9. **P2.0 — Temporal musical knowledge and shelf queries (future, exploratory).** Represent recording contributors, instruments, roles, time-bounded musical events and coordinated/overlapping passages with provenance and annotation coverage. Enable queries such as "my favorite songs with dual guitar solos" and "how many scrobbles of recordings with two guitar solos?" without claiming complete playback or treating missing annotations as negative evidence. Design and sequence only after the near-term canonical library is useful; no implementation authorization implied.

The primary security boundary is the local issuer/subject profile and its authenticated session. Last.fm association grants access to a public archive and does not prove source-account ownership. Identical same-second deliveries lack upstream durable event IDs; report this limitation rather than inventing certainty. Unresolved observed names are never canonical MusicBrainz artist/album/track entities.
