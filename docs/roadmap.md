# Muzeum numbered roadmap

Canonical roadmap, updated 2026-11-17. This file supersedes milestone ordering and authentication requirements in the dated repository assessment, January notes, P1.0 proposals and original P1.1 plan. Those documents remain historical evidence. Muzeum is the application; no legacy Muzeus database migration is planned.


## Product direction

**Primary daily use: "What am I pulling off my shelf next?"** Muzeum helps a listener explore, remember and choose from their own music, not merely maintain a catalog or browse raw scrobbles. Canonical identity, provenance, listening statistics and musical knowledge enable this. Near-term selection should work with existing counts, recency and relationships; future rich queries can intersect preferences with musician/instrument/event annotations. Preserve honest distinctions between Last.fm-reported scrobbles and actual playback completion.

## Canonical product specifications

The authoritative, living domain rules are [principles](domain/principles.md), [recording resolution](domain/recording-resolution.md), [release assignment](domain/release-assignment.md), and [listening statistics](domain/listening-statistics.md). They distinguish source observations, canonical recording identity, release membership, per-play credited release, automatic contextual reassessment, user overrides and disjoint release rankings. 4. **P1.3a — Canonical recording resolution.** Implemented exact archive surfaces, append-only listener surface assignments and scrobble exceptions, scoped reads, and a bounded MusicBrainz/Discogs assessment-only pilot. The [first live pilot](p1.3/live-provider-pilot-2026-11-17.md) completed four assessments with four abstentions. Review the evidence gaps and a broader labeled catalog sample before considering automatic acceptance. [Implementation and pilot](p1.3/README.md).
5. **P1.3b — Resolution workspace.** Build an authenticated Rails/Hotwire workspace for unresolved groups, original source details, candidate comparison, correction and auditable reversal. Later review interactions should distinguish suggested from applied changes and support Apply to all (surface), Only this time (scrobble), and Dismiss/defer, without overwriting manual exceptions. Use compact Muzeum conventions and verify isolation across users sharing an archive.
6. **P1.3c — Release relationships and contextual attribution.** Reconcile provider editions and track slots into Muzeum collection membership. Develop per-play credited release as independent history with contextual reassessment and user overrides. Review the open release policy questions before enabling defaults.
7. **P1.4 — Canonical Artists, Releases, Recordings and Plays library (tentative).** Build compact tables, search, filters, track listings and listening histories around canonical music. Membership views show all activity of included recordings. Release rankings use at most one credited release per play. Use Muzeus once as a visual reference and reflect new committed listens without refresh. Include a practical early shelf-selection experience using known recordings, frequency, recency and collection navigation. Design a deliberate artist/release/recording metadata contract and a repeatable **Import** action to refresh selected MusicBrainz/Discogs fields with provenance, comparison and safe change history; avoid indiscriminate provider mirroring.
8. **P1.5 — Richer reporting and refinements (tentative).** Add rebuildable, scoped aggregates, charts, durations and rankings as the interpretation contracts stabilize. Generic external recommendations, Spotify, playlists, streaming and social features remain deferred; **choosing and rediscovering from one's own shelf is not deferred**.

9. **P2.0 — Temporal musical knowledge and shelf queries (future, exploratory).** Represent recording contributors, instruments, roles, time-bounded musical events and coordinated/overlapping passages with provenance and annotation coverage. Enable queries such as "my favorite songs with dual guitar solos" and "how many scrobbles of recordings with two guitar solos?" without claiming complete playback or treating missing annotations as negative evidence. Design and sequence only after the near-term canonical library is useful; no implementation authorization implied.

The primary security boundary is the local issuer/subject profile and its authenticated session. Last.fm association grants access to a public archive and does not prove source-account ownership. Identical same-second deliveries lack upstream durable event IDs; report this limitation rather than inventing certainty. Unresolved observed names are never canonical MusicBrainz artist/album/track entities.
