## Evidence and prerequisites

Reviewed the current Gemfile/lock, Dockerfile, Kamal scaffold, database/Puma/queue/cable/production configuration, routes, ERB layout, GitHub Actions and P1.0 baseline/contracts. Rails is locked to 8.1.2, Ruby pinned to 3.3.5. Propshaft, Puma, Active Job, Solid Queue, Solid Cache and Solid Cable are present. Production declares primary, cache, queue and cable PostgreSQL databases. `bin/jobs` exists; Puma optionally embeds Solid Queue. The layout has CSS but no JavaScript entry point; importmap, Turbo, Stimulus, bcrypt, Capybara and Capistrano are not declared. Only `/up` is routed; authentication and product views are absent. SSL/proxy trust and host restrictions need configuration. The Kamal deployment uses a placeholder address and embeds jobs in Puma; it is not evidence of a running deployment and is not the chosen deployment mechanism.

GitHub Actions already triggers on every push to main and pull requests, with RSpec, RuboCop, Brakeman and bundler-audit. Scans and RSpec currently share sequential steps, so a failed scan can prevent tests from running; make required checks independently observable. Local `bin/ci` lacks RSpec. P1.0's dependency audit failed; findings require triage, not an assumption of a deployable baseline. `docs/ops.md` says PostgreSQL 15 while CI/baseline use 16. No actual server topology, Caddy imports, service manager, database ownership, capacity, backup policy or manual approval mechanism has been verified in this review. Do not infer these from scaffold files.

Before final infrastructure choices, obtain the server alias/access method and existing operations runbook. Perform an authorized **read-only** inventory: OS/architecture, Ruby tooling, service users/units and deployment layouts, listening ports, Caddy version/config/imports/TLS management, firewall, PostgreSQL version/topology/roles/databases (names and grants, no row contents), storage mounts/free space, RAM/CPU/swap, existing backup destination/retention/restore process, log rotation and monitoring. Inspect another application's deployment conventions without reading its credentials or changing it. Record existing-domain health and resource baselines. DNS records and IPv4/IPv6 routing for muzeum.fm must be checked before a separately approved DNS change. Do not SSH to guessed hosts or edit existing applications to accommodate Muzeum.

## Proposed isolated layout and runtime

All names, paths, ports and budgets below are proposed until inventory confirms compatibility.

| Area | Proposed requirement |
| --- | --- |
| Deployment | Capistrano with Rails/Bundler integration, locked dependencies and an explicit production stage; no Kamal proxy/container rollout |
| Files | `/srv/muzeum/releases/<timestamp>`, `current` symlink, `shared`, Capistrano repository cache and revision log; retain five known releases subject to disk budget |
| Persistent state | Link shared configuration, `storage`, logs and runtime directories as appropriate; database data lives outside releases under independently owned PostgreSQL storage; never clean shared state with release cleanup |
| Identity | Dedicated Muzeum deployment/runtime identity or separate deploy/runtime users following host conventions; scoped repository read credential, verified SSH host key, no broad sudo or shared app secrets |
| Web | `muzeum-web.service`, Puma bound only to an allocated loopback port or Caddy-accessible Unix socket; never take public 80/443 from Caddy |
| Jobs | `muzeum-worker.service` running `bin/jobs`; `SOLID_QUEUE_IN_PUMA` absent (setting it to the string `false` still enables the conditional); graceful shutdown, bounded restart policy |
| Queue isolation | In P1.2/P1.4 use separate ingestion/resolution queue consumers and independently restartable units, with explicit queue lists and one designated dispatcher/scheduler arrangement; no wildcard worker accidentally consuming both |
| Proxy | Add only a muzeum.fm site through the existing Caddy configuration convention; HTTPS terminates there, reverse proxy to Muzeum, preserve all other hosts |

Start with one Puma process/three threads and one worker process/one job thread. Proposed Muzeum slice ceiling: 2 GiB memory and 100% CPU (one core equivalent), web MemoryHigh 512 MiB/MemoryMax 768 MiB, workers collectively MemoryHigh 768 MiB/MemoryMax 1 GiB, bounded tasks/file descriptors and restart backoff. These are acceptance candidates, not safe allocations until host headroom is measured. Apply through the existing service manager's resource controls; leave capacity for PostgreSQL, Caddy and other apps. Bound database connection pools per process and per database including queue dispatcher, cable and maintenance connections; enforce an app role connection limit after measuring the total. Watch disk/WAL/backups/raw-page growth, and pause import before exhausting shared capacity. Do not change global PostgreSQL limits, host packages or other services without separate review. A shared PG cluster cannot provide a hard per-database memory ceiling; choose an isolated instance only if inventory shows that necessary and affordable.

## PostgreSQL ownership, backups and migrations

Retain the four configured Muzeum databases initially unless review justifies consolidation. Use an explicit Muzeum owner/migrator role and restricted runtime role(s), no superuser/CREATEDB/CREATEROLE runtime access, and no grants on other applications. Review schema ownership/default privileges and queue/cache/cable DML requirements. Restrict connectivity to local socket/loopback or the established private database path. Record database names, role grants, server version and physical storage ownership in the operator runbook. CI/local tests must match the chosen production major version; do not upgrade the shared cluster to match the current CI image.

Before first deploy, inventory whether Muzeum data exists; retain IDs, payloads, source lineage and counts. Use explicit database-specific migrations against the approved target, never production `db:reset`, `db:drop`, schema load or unconditional seeds. Fresh database provisioning is a distinct approved bootstrap operation, not a deploy hook that recreates missing databases silently. Rehearse primary and auxiliary database bootstrap/migrations in disposable databases. Adopt additive expand/backfill/validate/contract changes, bounded restartable backfills, lock/statement timeouts, and concurrent index operations where needed. Pause incompatible writers at cutover; document old/new code and job payload compatibility. P1.2 owns the account/provenance transition; P1.1 adds only the auth/infrastructure schema it needs.

Proposed backup policy, pending storage/retention approval: encrypted nightly custom-format `pg_dump` of each Muzeum database to an off-host destination, seven daily and four weekly copies, plus pre-migration backups; include shared storage and separately protected secret recovery material. Capture role/grant recreation instructions scoped to Muzeum, not an automatic cluster-wide globals restore. Assign an operator owner and failure notification destination; inspect backup freshness/size/checksum and alert after 24 hours. Provisional RPO 24 hours and RTO four hours require a timed restore drill. If unacceptable, design continuous WAL/PITR with the existing PostgreSQL operator; do not enable it globally as an incidental app change.

Restore drill: restore dumps to new isolated Muzeum-named databases, recreate scoped ownership/grants, verify schema versions, row counts/source checksums, attachments and login, and reconcile queue jobs with primary data. Independent dumps are not a cross-database atomic snapshot: pause enqueues/workers/writers for coordinated recovery checkpoints or document deduplication/reconciliation of pending jobs. Queue contents are operational state, never the sole import checkpoint. Cache/cable may be rebuilt under an explicit policy. Never restore over another application's database. Restoring production loses writes since the backup and requires explicit approval and downtime.

## Authentication and Rails-native UI

P1.1 includes local Muzeum authentication before any personal data or resolution controls become reachable: adapt Rails authentication patterns to existing Users, bcrypt, revocable server sessions, explicit operator provisioning, login throttling, CSRF protection, secure cookies, session expiry/revocation and server-side account permissions. Preserve existing User IDs and do not treat Last.fm usernames as login proof. No open registration is required. Until SMTP is configured, document an operator reset procedure rather than exposing broken password recovery. No public history default, admin console, import dashboard or resolution endpoint. Public liveness and sign-in may expose only nonsensitive information. Authorization must also cover downloads, Turbo Frames/Streams, subscriptions and worker execution; hiding a link is insufficient.

Use Rails 8 RESTful controllers, ERB layouts/partials and reusable accessible views. Retain Propshaft; plan minimal reviewed additions of importmap-rails, turbo-rails and stimulus-rails after the application review above, with import-map tags/entry points and asset verification. Turbo Drive supplies navigation, Frames independent sections/forms, Streams authorized progress updates where valuable, and Stimulus focused interactions. Business rules, authorization, search, filtering, pagination and resolution stay server-side. No React, Vue, SPA or extra frontend API layer. Bundling needs a documented concrete requirement before adoption. Follow the [Rails JavaScript guidance](https://guides.rubyonrails.org/working_with_javascript_in_rails.html).

Use Active Job/Solid Queue independently of web. Action Cable/Solid Cable may deliver Turbo Streams when useful; scoped authenticated subscriptions must recheck revocation, and reconnect/page reload must recover progress from the database. Polling a server-rendered Frame is an acceptable initial alternative. Configure proxy WebSocket behavior, allowed origins and session scope before enabling streams. Private views must not leak through shared caches or PWA caching. Responsive semantic tables/forms, keyboard access, labels, focus/error handling, contrast and status announcements are acceptance criteria.

Add Capybara with Rails system tests and a supported browser driver for login/logout, access denial, CSRF/session behavior and subsequent Turbo flows; retain RSpec for model/service/request coverage. Run browser tests explicitly in CI (including `rails test:system` if using Rails' system-test harness alongside RSpec), with deterministic local fixtures, no live providers or production credentials.

## CI and explicit deployment workflow

Every push to main must run GitHub Actions RSpec, RuboCop, Brakeman and dependency security checks, plus system tests as introduced. Preserve PR checks, use disposable PostgreSQL, and make local `bin/ci` equivalent. No deployment trigger, production secret, deploy key, SSH action or automatic release hook belongs in CI. Do not auto-upgrade gems or silently suppress audit exit codes. Capture advisory IDs, severity, affected version/path, runtime applicability, mitigation and owner. Block applicable critical/high findings pending remediation; lower-severity or nonapplicable findings require recorded rationale and explicit risk acceptance, review/expiry date and narrow advisory-specific exceptions if needed. Scanner failures stay visible; deployment authorization names any accepted exceptions. A failed database update/network scan is an incomplete audit, not a pass.

Deployment is manually initiated after explicit authorization under the existing approval workflow, whose exact mechanism must be discovered. The approval records target host, immutable full Git SHA, CI run/results for that exact SHA (prefer passing), audit exceptions, migrations, backup ID, expected interruption and rollback boundary. No deploying a moving `main` tip. Planned Capistrano tasks must require an approved SHA, set checkout revision from it, verify the deployed `REVISION`, and abort on missing/mismatched approval inputs. Future command shape: `bundle exec cap production deploy APPROVED_SHA=<full-sha>`; this variable/task is a requirement to implement, not an existing supported command. Never push as a side effect of deploy.

Capistrano prepares a new release, links shared configuration/storage, installs locked gems, precompiles Propshaft/importmap assets, verifies configuration and takes the approved migration path before switching `current`. Migration execution is single-operator, serialized and scoped to Muzeum databases. Restart only Muzeum services; validate the actual running revision, not just the symlink. Keep previous fingerprinted assets available for in-flight pages. Implement failure hooks that record whether migrations ran and whether the symlink changed, without automatically restoring data. The [Capistrano directory structure](https://capistranorb.com/documentation/getting-started/structure/) and [rollback flow](https://capistranorb.com/documentation/getting-started/rollbacks/) are the operating model.

## Verification and rollout gates

1. Local review: meaningful auth/request/system tests, all required CI checks and documented audit triage; boot/asset build with production-like config and no provider requirement. Test migration forward and previous-release compatibility on a restored disposable Muzeum dataset. No real full historical import locally; synthetic 250k tests belong to P1.2.
2. Before production changes: explicit approved SHA/scope, confirmed host inventory/headroom, DNS/Caddy diff, successful backup/restore evidence, secret provisioning and service/resource configuration review. Infrastructure, DNS, deployment and production database operations each need explicit authorization covering their action.
3. Bind the initial app privately and verify sign-in/access isolation before domain exposure. Configure muzeum.fm host validation, trusted proxy/forwarded HTTPS behavior, secure cookies and HTTPS redirects without loops. Confirm no public DB, Puma, debug, job dashboard or admin port.
4. Validate the complete candidate Caddy config and review a diff affecting only muzeum.fm; use the established graceful reload method after approval, never stop/restart shared Caddy casually. Verify certificate issuance/renewal path, HTTP redirect, HTTPS, asset delivery and existing domains against the baseline. See [Caddy validate/reload](https://caddyserver.com/docs/command-line).
5. Post-deploy: nonsensitive `/up` liveness over HTTPS plus protected readiness for primary/queue DB access, migration state and worker heartbeat; authenticated smoke test and unauthenticated direct URL/Frame/subscription denial. Enqueue a harmless test job, independently restart web and worker, confirm durable completion/recovery, resource use and revision. `/up` alone does not prove database or worker health.
6. Operational handoff: `systemctl status muzeum-web muzeum-worker` and scoped `journalctl -u` procedures adapted to verified units; Caddy access/error logs using existing conventions, bounded journal/log retention, request IDs, job/run IDs and sanitized failures. Never log keys, passwords, raw private listening payloads or session tokens. Monitor error rate/latency, worker heartbeat/backlog/retries, import progress, DB connections, disk and backup age; identify alert recipient and thresholds before unattended jobs. Record release SHA, operator, approval, migration versions and checks.

## Rollback and failure procedure

Stop the rollout on failed preflight; leave `current` and shared proxy unchanged. If failed after migrations but before symlink switch, assess schema compatibility before restarting old code; do not assume a failed deploy leaves the database unchanged.

For a bad release with compatible schema: pause Muzeum enqueues, gracefully stop/drain Muzeum workers, record checkpoint/job state, invoke reviewed `bundle exec cap production deploy:rollback` to the verified previous release, restart only Muzeum web/workers, and repeat health/auth/job/domain checks. Confirm previous code understands queued job arguments. Shared secrets/storage/databases persist across releases; rollback does not revert them. Revert a Muzeum-only Caddy change via the saved configuration, validate the whole config, then gracefully reload and recheck all domains if necessary. First deployment has no previous release: disable only the Muzeum route/services and preserve data for repair.

Capistrano code rollback does **not** reverse database migrations. Prefer a compatible forward fix; destructive/irreversible changes or incompatible backfills may prohibit old-code rollback. Each release documents migrations, lock impact, reversibility, allowed previous version and tested recovery. Never automatically run `db:rollback` or restore a dump. If restoration is required, obtain explicit approval for data loss/downtime, stop only Muzeum writers/workers, restore to isolated replacement databases, validate/reconcile before redirecting Muzeum connections, and retain failed state for investigation. DNS rollback depends on TTL and is not an immediate service recovery mechanism.

P1.1 exit: an independently managed, authenticated production foundation with verified HTTPS, persistent storage, restore rehearsal, CI/deploy separation, worker independence and documented rollback. The actual initial deployment remains an explicitly approved future action. P1.2 historical ingestion cannot start until these gates pass.
