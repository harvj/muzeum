# P1.1a deployment preparation and runbook

> Historical milestone record. The [canonical numbered roadmap](../roadmap.md) and P1.1d requirements supersede the local-password and import-ordering assumptions below.
Prepared locally, not deployed. Read the [verified inventory](infrastructure-inventory.md) and [production plan](production-deployment-plan.md). Configuration uses the verified `/var/www`, systemd, Caddy and PostgreSQL 16 conventions. Dedicated Muzeum identity and port are proposed additions, not existing resources. P1.1b removes the obsolete Docker/Kamal/Thruster scaffold; Capistrano is the application deployment mechanism.

## Exact proposed server changes (all pending explicit approval)

1. Create dedicated OS user/group `muzeum` with home `/home/muzeum` and app directory `/var/www/muzeum`; install Ruby 3.4.12 with RubyGems/Bundler 4.1.0 under this identity without changing deploy's Ruby 3.4.8. Supply scoped GitHub read-only repository credential and verified host keys. Configure SSH access for authorized deployment operator, no agent forwarding.
2. Create `/var/www/muzeum/{releases,shared}` and shared `.env`, `.env.migrate`, storage/log/tmp directories, owned by Muzeum; secret files mode 0600. Use the environment example as names only. `.env` has runtime credentials, `.env.migrate` has scoped owner/migrator credentials plus required app environment; shell-compatible systemd assignments, never shell substitutions. Link runtime `.env` only. Runtime must never use SECRET_KEY_BASE_DUMMY or SOLID_QUEUE_IN_PUMA. Real Rails master key/secret key stay out of Git/CI.
3. Create `muzeum_owner` NOLOGIN, `muzeum_migrator` login authorized only for Muzeum ownership/migrations, and `muzeum_runtime` login with only required connect/schema usage/table/sequence DML grants. Create `muzeum_production`, `_cache`, `_queue`, `_cable` owned by Muzeum owner; set default privileges for migrator-created objects to runtime. No superuser/CREATEDB/CREATEROLE app privileges or other-app grants. Bootstrap all four schemas explicitly in empty Muzeum databases only; never schema-load a populated database. Review actual SQL/connection limits before execution; no SQL provisioning has been run.
4. Establish encrypted off-host Muzeum database/shared-storage backups, named owner/alerts, retention and a measured restore rehearsal before deployment. Approved retention is 30 daily/12 weekly/12 monthly; RPO 24h/RTO 4h still require acceptance against measured production recovery. See [current backup activation gates](../p1.1c/backup-activation-readiness.md). Do not reuse another application's backup files or policies implicitly.
5. Install only the two reviewed `config/deploy/templates/muzeum-*.service` units, then daemon-reload and start/enable them only during approved rollout. Limits aggregate to at most one CPU and 1.75 GiB process memory plus PG overhead. Worker has one process/one thread; future import/resolution services remain separate work. Give deployment identity narrow sudo permission to restart only these named units. Review service unit writes as a separate privileged step.
6. Append only the reviewed `muzeum.caddy` site block to `/etc/caddy/Caddyfile`; preserve all existing blocks including funding authentication. Validate full config, then `systemctl reload caddy`; never overwrite or restart shared proxy. Port 3011 is loopback-only; recheck availability. DNS changes, if needed after checking A/AAAA, need separate approval; no other firewall/domain changes proposed.
7. Deploy approved code, explicitly authorize migrations of Muzeum databases and provision initial local principal interactively. No historical import, resolver or unrelated service/database operations.

## Local validation and approval packet

CI on every main push runs independent RSpec/system, RuboCop, Brakeman and updated dependency audit jobs. No production credentials or deployment trigger. Browser-enabled CI uses Capybara/RSpec Rails system tests and headless Chrome; local `BROWSER_TESTS=1` selects the same browser path, `CHROME_BINARY` may select installed Chromium. Without the flag, Capybara uses RackTest (no JavaScript). No auto-upgrades or ignored advisory failures. P1.1b resolves the prior dependency findings; see the [modernization report](../p1.1b/dependency-modernization.md). The original [P1.1a results](p11a-results.md) remain historical.

Before deployment, record full SHA, exact-SHA CI results, explicit deployment/migration approvals, backup ID, target host, expected interruption, schema compatibility, audit dispositions and rollback target SHA. The existing manual authorization is a human approval record; no new automated deploy workflow is introduced. Operator sets the documented reference flags only after that authorization; the flags are guardrails, not an external approval verification service.

Configuration/task listing is safe locally: `bundle exec cap production -T`. Do not run `deploy:check` as a read-only inventory command: Capistrano creates directories. Deployment entry point is deliberately blocked without APPROVED_SHA, APPROVAL_REF and INFRASTRUCTURE_READY=yes; migration hook additionally requires MIGRATION_APPROVAL_REF and BACKUP_ID. No remote deploy task was executed in P1.1a.

Future authorized command shape (not authorization to execute):

```sh
APPROVED_SHA=<full-approved-40-character-sha> APPROVAL_REF=<record> \
INFRASTRUCTURE_READY=yes MIGRATION_APPROVAL_REF=<record> BACKUP_ID=<verified-backup> \
bundle exec cap production deploy
```

Capistrano checks out that SHA, prepares release/shared links, installs locked dependencies and builds assets with a dummy build-only key. The explicit custom migration hook sources shared `.env.migrate` and runs migrations from the prepared release before publishing; it does not create/drop databases or load schemas/seeds. Ensure all writers are paused for incompatible changes and no second deployment runs concurrently. Production default connection URLs must be verified for all four databases, not inherited from development. Auxiliary initial schema bootstrap is a separate prerequisite; `db:migrate` does not substitute for loading those explicitly into new databases.

Capistrano switches `current`, restarts only Muzeum services, checks REVISION against approved SHA, unit activity and loopback `/up`. These automated checks do not prove worker throughput, real authentication, database permissions or all-domain health: perform the manual checks below. Secrets and storage survive release cleanup; keep five releases and retained fingerprinted assets. Do not print environment files or pass passwords as command arguments.

## Authentication provisioning and access policy

No self-registration, OAuth, provider ownership inference or public personal data. User IDs and source payloads are retained. `lastfm_username` remains optional transitional lineage; new local users need none, legacy users remain inactive without explicit provisioning. No LastfmAccount transition/backfill is attempted in P1.1a; P1.2 adds account associations. The only authenticated page is the current user's landing page; no target user parameter, history, import or resolution route is exposed. All future controllers inherit authentication and must add explicit account authorization; authentication alone is not an archive grant.

Inside an approved production operator session, load the protected app environment without echo, then run `bundle exec rake users:provision` on a TTY to create a local login. To activate/reset a specifically reviewed existing ID use `bundle exec rake 'users:provision[ID]'`. Password is entered without echo/argv/history. Never choose an existing user by Last.fm username automatically. Password updates revoke sessions. Disable via an approved console update of `disabled_at`; this revokes sessions. No reset-email route until delivery is configured. Default Cable and Active Storage routes are disabled until scoped subscription/download authorization exists. Sessions expire after 12h; cookies are signed, HttpOnly, SameSite=Lax and Secure in production. Rate limiting uses Rails cache (Solid Cache in production). Sessions and private responses are not publicly cacheable. Schedule reviewed expiry cleanup later; no personal-data dashboard is added.

## PostgreSQL backup/restore and rollback

Before migration: pause Muzeum writers/enqueues/workers at transaction boundaries and capture per-database custom-format `pg_dump`, checksums, migration versions, source counts/digests and shared-storage snapshot; encrypt and copy off-host. Keep secrets in separate protected recovery storage. Four independent dumps are not atomic across databases: quiesce or reconcile queue jobs explicitly. `pg_restore --list` is only readability inspection, not a restore drill. Test restoration into *new isolated* database names using `pg_restore --no-owner --no-acl`, reapply scoped owner/grants, then verify schema/data/login/storage and queue reconciliation. Do not drop/restore any existing other-app database; no cluster-wide globals restore. Never use production reset/drop/schema-load or seeds during a normal deployment.

Auth migration is additive except relaxing lastfm_username nullability (retains all existing values); old source-only rows remain inactive. Its down direction deliberately refuses to delete credentials/sessions or force provider names onto local-only users. Previous code can run against added fields, but cannot authenticate; do not expose private routes if reverting. Each later release must state lock/backfill impact, compatible prior version and irreversible operations.

On failure before publish, inspect whether migrations committed; leave current code and Caddy unchanged. For compatible code rollback: stop/drain only Muzeum jobs, record current/checkpoint state, approve the prior release SHA, then invoke `bundle exec cap production deploy:rollback` with APPROVED_SHA set to the expected previous release, APPROVAL_REF and INFRASTRUCTURE_READY=yes. Verify the target REVISION, restart only Muzeum units, and repeat auth/job/domain checks. Queue payload compatibility must be reviewed first. Capistrano does not revert DB migrations, secrets or shared storage. Never automatically invoke db:rollback or restore a dump.

First deploy has no previous release: stop only Muzeum units and remove/disable only its Caddy block through validated reload; preserve DB/storage. For incompatible schema failure prefer forward fix; restoring production requires new explicit approval for downtime/data loss since backup, isolated replacement databases, validation/reconciliation and scoped connection cutover. DNS TTL makes DNS rollback noninstantaneous. Pending restore proof and runtime provisioning prevent production readiness. P1.1b upgraded Solid Queue to 1.7.2: its additive queue migration preserves existing jobs and adds batch tables/indexes. Bootstrap new auxiliary databases from their current schema files; on existing queues apply db:migrate:queue rather than loading a schema. The migration refuses destructive down rollback; retain batch/job state. Ruby 3.4.12 must be provisioned separately; older code rollback also needs its compatible runtime/bundle available. Native libvips is needed only if image variants are enabled; those routes remain disabled.
