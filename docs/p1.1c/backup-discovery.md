## Prepared implementation design (not installed)

Use dedicated root-controlled `/etc/muzeum-backup` credentials/configuration and separate `/var/lib/muzeum-backup` staging/cache/state, never application-readable backup credentials. Install Restic from a verified vendor/package source only once the destination is available. Pin the SFTP host identity with StrictHostKeyChecking=yes, IdentitiesOnly=yes, a dedicated key and known_hosts file, no agent forwarding. Only the public backup key is added to the Muzeum subaccount; storage/Restic passwords never appear in argv, Git, unit text or logs. Restic encryption password and SSH recovery material must also be escrowed outside this server/repository so loss of the host does not make its backup undecryptable.

[Hetzner supports Restic's SFTP backend](https://docs.hetzner.com/storage/storage-box/access/access-ssh-rsync-borg/), and [subaccounts share capacity but are confined to their directories](https://docs.hetzner.com/storage/storage-box/general/). Use separate repository encryption passwords and SSH keys per app; never reuse the main account in a backup unit. Treat separate Restic keys on one repository as shared data authority, not per-application isolation.

For Muzeum's four databases, use an explicit allowlist and PostgreSQL custom-format dumps with durable defaults and bounded compression. Avoid per-database URL discovery from unrelated apps. Each pg_dump is internally consistent, but four dumps are not one cross-database atomic snapshot. Quiesce **only Muzeum** web/enqueues/workers for a coordinated backup, preserve prior active state, complete and checksum dumps plus persistent files/secrets/revision/schema manifest, then restore prior services even on failure. Publish/upload only a complete capture; do not mark partial dumps successful. Longer-term queue-aware reconciliation can reduce downtime, but is not assumed implemented. Initial proof uses disposable test databases/files only; no Muzeum production DBs exist yet.

Include shared storage, protected runtime/migration configuration, dedicated Rails credential/secret recovery material, app-specific units/grants/bootstrap instructions and approved release SHA. Exclude repository passwords/SSH private keys from the application recovery payload itself; escrow them separately. Do not rely on the checked-in encrypted Rails credentials when no matching key is available. No local config/master.key was found during preflight; production secret provisioning remains a deployment prerequisite.

Proposed systemd jobs: `muzeum-backup.service` + daily 02:00 UTC timer with Persistent=true and up to fifteen minutes jitter; weekly integrity-check job; independent stale-success monitor. Serialize with an app backup lock and a shared backup resource lock for later adoption. Candidate limits: CPUQuota=25%, MemoryMax=1 GiB, Nice=10, idle I/O scheduling with device bandwidth limits, one PostgreSQL dump process and bounded SFTP connections/upload bandwidth; timeout two hours. Select and enforce a finite staging volume/quota, reserve disk headroom and fail closed before capture if the budget is insufficient. Directory size checks alone are not a hard disk limit. Verify unit/resource behavior before unattended execution. No timer is enabled without a verified target and tested alert channel.

Persist a sanitized last-success timestamp/snapshot ID, capture/transfer/check durations and bytes. Nonzero dump/Restic/restore/check status, insufficient disk, broken credentials, network interruption or stale success (>26 hours) must fail visibly; OnFailure should notify through the configured route, and stale-success monitoring must detect a disabled timer too. Do not report success merely because a process launched or a dump can be listed. No alerts have been sent or monitoring installed.

Retention uses stable tags and paths so each daily run belongs to the same application retention group. After recovery proof, the policy shape is:

```sh
restic forget --tag app:muzeum,env:production --group-by host,tags \
  --keep-daily 30 --keep-weekly 12 --keep-monthly 12 --dry-run
```

Initially only the dry run is permitted: **neither forget nor prune is scheduled/enabled**. Both can remove recovery material; require successful backup, restored application/data proof, repository integrity checks and a reviewed plan before removing --dry-run or enabling pruning. Serialize later prune/check jobs with backup jobs and bound their resource use. Restic retention counts nonempty daily/weekly/monthly periods and combines keep policies, not 54 guaranteed distinct backups. See [Restic retention behavior](https://restic.readthedocs.io/en/stable/060_forget.html).

SFTP write access can also delete repository files; Restic encryption is confidentiality/integrity protection, **not append-only storage**. Dedicated subaccounts limit compromise to one app's directory, but cannot alone prevent that app's credential from damaging its repository. Enable Storage Box automatic snapshots managed through separate Hetzner-account credentials/MFA kept off the server; verify a compromised subaccount cannot administer snapshots. Agree schedule/slots only after discovering the Box and other consumers. Snapshots consume shared capacity and do not constitute an independent second provider copy. A whole-Box rollback would affect every application's repositories: independent recovery must copy the selected repository/files from a snapshot into an isolated target rather than roll the shared Box back. [Hetzner snapshot semantics](https://docs.hetzner.com/storage/storage-box/snapshots/).

3. Read that exact snapshot back from SFTP into a new isolated directory. Verify full file hashes. Restore custom dumps with pg_restore --exit-on-error --no-owner --no-acl into uniquely prefixed disposable databases, recreate only scoped test grants and compare schema versions, counts, fixture/source checksums, job state and file integrity. Run application compatibility/login and harmless queue checks using only those targets.
4. Run Restic repository checks, including full data read for initial proof; archive sanitized status/durations. `pg_restore --list`, same-host restore without retrieving the off-host snapshot, and a successful upload alone are insufficient.
5. Inject bad-credential/unreachable-endpoint and failed dump scenarios against disposable targets; demonstrate failed status, no new success timestamp, safe staging/lock behavior and delivered failure plus stale-success alerts. Do not break the live repository/production credentials to simulate failure.
6. Record measured restore time and a reviewed RPO/RTO; provisional daily RPO 24 hours/RTO four hours is not an achieved result. Retain existing backup mechanisms throughout. Cleanup is limited to positively identified disposable test resources.

Recovery command form after provisioning (placeholders are not a runnable ready state): `restic restore <verified-snapshot-id> --target <new-isolated-directory>`, followed by scoped `createdb` and `pg_restore --no-owner --no-acl --exit-on-error --dbname=<new-disposable-db> <restored-dump>`. Restore never defaults to a production database, never loads cluster-wide globals, and never changes other applications' connections.
