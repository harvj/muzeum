# Source accounts, provenance and synchronization

## Identity and authority

`User` remains the existing Auth issuer/subject principal. `LastfmAccount` owns one source archive, immutable initial fingerprint identity key and original archive-user lineage. Active `UserLastfmAccount` grants allow multiple independent users to view/import that archive; interpretation permission is separate and never authorizes changing source records or another user's future decisions. Association validates a **public** username; ownership stays unverified. Removing a grant retains history and stops that user's access. Disabling a local principal also stops its import authority. Background ingestion does not depend on browser sessions or visitors.

Names use a case-folded unique lookup and an immutable reserved-name registry. Casing in an API response does not create a new account or silently rename the stored name. An alias of a renamed account cannot silently attach to a newly reported user with the old name. `reconcile_name!` requires explicit operator reason, independent username validation, no active run and no name conflict; the source identity/fingerprints stay fixed and synchronization pauses pending review. Conflicting archives are never merged automatically.

New browser associations can enable that source's schedule only after the global operator gate is enabled. The registered worker actor is `lastfm-scheduler-v1`; its allowlist is `sync_enabled` active accounts with an active local import membership and enabled OIDC-mapped local principal. Each page rechecks this policy before fetching and inside the commit transaction. User-requested work additionally checks the original requester. If that requester loses access while another valid grant remains, a new service-attributed run can continue the exact checkpoint with an immutable predecessor reference. It does not pretend the original user still authorized the work. Provider-side membership removal is enforced by existing OIDC admission on interactive access; operators must also revoke local source grants/disable the principal when withdrawing durable source-worker authorization. The worker does not depend on an expiring browser refresh grant.

## Additive schema and preservation

Three migrations add account/grant/name tables; nullable account columns are mapped in bounded primary-key batches, indexed concurrently, then required. Existing observation IDs, user lineage, timestamps, payloads, fingerprints, first-page references, raw pages, checkpoints and Auth identities are retained. Completed audited legacy traversal bounds seed `synced_through`; synchronization therefore starts incrementally, not with another full production backfill. Old user/name uniqueness is removed to permit sharing; account-scoped fingerprint uniqueness replaces user identity as the source boundary. Existing user-scoped indexes/lineage remain for retention and explicit compatibility review.

`SourceFetch` retains original response **bytes**, SHA-256, requested page/bounds/parameters, phase, time, retry number and error type, independently of the page transaction. Network/envelope errors retain available bodies; credential-bearing URLs are never persisted. `ImportPage` remains the immutable successful raw-page record. `PageCommit` links the successful receipt to the committed page and counters. `SourceDelivery` provides account, original-page position, observation ID where applicable, classification and canonical item checksum. The full original XML is on the fetch/page; no metadata is silently copied over an earlier observation. `IngestionIssue` records repeats, collisions, metadata differences, malformed/undated/now-playing items, out-of-window evidence, source drift and retry history.

A restartable `lastfm:backfill_provenance` task indexes **existing** pages only. It cannot insert observations, change source rows or advance old checkpoints. Legacy fetch time is explicitly the original page's recorded time, not an invented measured request time. Historical actor lineage remains `legacy`; unknown old authorization and retry history are not manufactured.

Database triggers prohibit source/evidence updates, deletion and truncation, including source-account reassignment and observation-ID changes. Account identity and import origin/bounds/actor context are immutable. Database checks recompute raw-fetch checksums, validate classifications and enforce matching page/run/account evidence. Down migrations deliberately refuse data loss. No canonical or interpretation tables are created or populated.

## Page processing and recovery

Each job handles one bounded page. A session-level PostgreSQL advisory lock serializes the entire fetch/commit for a source account; different accounts share the global request budget. The fetch receipt commits separately. A subsequent transaction locks the account/run, rechecks permission, bulk inserts distinguishable source tuples, records every delivery and issue, commits the raw page and advances the checkpoint. Failure before commit leaves the source cursor unchanged; acknowledgment loss after commit safely resumes from the committed state. Queues are delivery hints, not the source cursor.

Fingerprints retain the original version: immutable account identity key plus exact timestamp/artist/album/track tuple. Missing canonical identities are irrelevant. Repeated tuples do not increment event counts. Different tuples at one second remain separate **observations**, with collision issues rather than an unsupported claim about distinct plays. Changed MBID/loved/image evidence is retained without rewriting first payloads. Source lookup buffers are bounded by incoming fingerprints; grouped timestamp counts detect crowded seconds without loading entire buckets.

Every page's oldest second receives an explicit exact-second sweep, paginated if it exceeds 200 items. Desired interval bounds are recorded separately from actual overlapping `from`/`to` parameters. Undated, now-playing, invalid and out-of-window items remain evidence and never become listening events. Empty/malformed responses cannot advance a nonempty history. Fixed upper bounds prevent newer completions shifting historical pages; changing totals trigger evidence and pause/replay rather than false completion. Incremental intervals may replay automatically up to three generations with the **same bounds**; repeated drift or historical drift requires operator review. Same-total upstream edits/deletions remain fundamentally uncertain.

## Central scheduling and capacity

Solid Queue runs one central dispatcher every second. It uses the indexed oldest-due ordering and `FOR UPDATE SKIP LOCKED`, with a 30-second durable dispatch lease. Account state/run checkpoints survive process restarts. Enqueue happens after the primary transaction because queue and primary are separate databases; an enqueue failure is reclaimed from the lease. Duplicate jobs are harmless under source locking and due-time checks.

All Last.fm calls, including username validation, use a PostgreSQL singleton request budget: default **one start/second**, configurable downward with `LASTFM_REQUESTS_PER_SECOND` (0.01–1). HTTP 429/Retry-After, envelope 29 and provider outages produce durable backoff. Five rapid failures enter a longer circuit-breaker pause; recovery probes back off to six hours. Permanent access/key failures pause for operator action. Shared limiting deferral is not a provider failure and does not consume the retry budget. Database errors retain the cursor/receipt and either persist a sanitized pause or remain visible to queue failure handling until the database recovers.

Recent activity keeps the small-account interval near 45 seconds; quiet sources back off toward an hour. A population/capacity floor increases intervals at scale and gives quieter sources longer waits. Fair per-page scheduling lets large runs progress without monopolizing all work. Historical and incremental writers use the same lock, budget and provenance. Incremental windows overlap the prior watermark by 48 hours and cap traversal width at seven days, draining long outages without skipping the intervening range. Changes older than the lookback require reviewed replay. Poll completion and observation/event freshness are measured separately.

## Dashboard and P1.3 boundary

The dashboard queries only actively associated archives and displays persisted source counts, committed progress, last successful poll, watermark lag, failures and exclusions. Visible authenticated pages request a versioned update every ten seconds; unchanged versions return 204 before expensive statistics. Changed data arrives as a Rails Turbo Stream replacement. Hidden pages stop checks, and pages with no association do not poll. These HTTP requests never call Last.fm. Authorization is rechecked for every update; revoked grants remove the old archive from the response. OIDC, CSRF, navigation and environmental assets remain independent.

P1.3 must insert newly committed observations into an open authenticated timeline automatically, using a similarly scoped Turbo Stream/update contract, stable observation IDs and keyset ordering. It must recheck access on update delivery and handle missed updates/reconnection. P1.2 deliberately does not build that timeline, search, Now Playing, MusicBrainz/Discogs resolution or derived listening aggregates.
